# ork-recipes — published per-model routing recipes.
#
# Tuning is DATA, not knobs. The right routing for a model cannot be guessed (this project has had
# microbenchmarks predict wins that measured as 3-5x regressions), and making every user sweep for it is
# worse than measuring once and publishing. Drop this file at one of the searched paths and ggml-ork picks
# it up at model load — no recompile, no repack.
#
# Searched, first match wins:
#   $ORK_RECIPES  ·  ./ork-recipes.txt  ·  ~/.config/ork/recipes.txt  ·  /etc/ork/recipes.txt
# An external row overrides the compiled-in table. A locally measured pack calibration outranks both (it
# was measured on THAT machine and re-verified against it). ORK_DECODE_ROUTE is a development override.
#
# KEY = (model shape fingerprint x SoC). A shape tuple rather than a name, because what decides whether a
# route pays is geometry against achieved bandwidth — so two fine-tunes of one architecture inherit the
# same recipe automatically. Read the fingerprint off any run:
#     [ORK RECIPE] model fingerprint: n_layer=.. n_embd=.. n_ff=.. attn_kv=.. soc=..
#
# SoC is part of the key and rows apply ONLY on a match: a recipe measured on a board with the A76s
# unlocked to 2400 MHz and a custom kernel must not be applied blind to a stock board. Anything unmatched
# falls back to the safe default — which is also the measured-best config on every model so far, so an
# absent model loses nothing.
#
# decode_route:  0 = decode on CPU (the measured-best default everywhere so far)
#                1 = dense M==1 matmuls on the NPU
#                2 = + fused FFN decode chain and q,k,v / gate-up group fusion at M==1
# min_m:         routing threshold; 0 = leave to the default/calibration.
#
# ALL ROWS MEASURED 2026-09-04 on rk3588 (A76 @2400 MHz, kernel 6.1.115 #70, governors performance),
# ork_bench P=512 G=32, route 0 vs route 2 (and route 1 where it mattered).
#
# soc     n_layer  n_embd   n_ff  attn_kv  decode_route  min_m
rk3588         28    1024   3072     1024             0      0   # qwen3-0.6b-f16      CPU 15.70 vs r2 5.12-5.58 (NPU 2.8-3x slower)
rk3588         28    2048  12288     1024             0      0   # qwen3-1.7b f16+q8_0 CPU 10.21 vs r2 10.36 (tie in noise) — ONE row covers both source precisions
rk3588         28    1536  17920      256             0      0   # qwen2.5-1.5b-q8_0   CPU 11.51 vs r2 11.48 (tie in noise)
rk3588         24    1024   3584        0             1      0   # qwen3.5-0.8b-bf16   *** NPU WINS *** CPU 2.44 vs r1 3.40 (1.40x after the doorbell big-core fix; was 1.28x before it)
#
# NOT keyable, measured and left on the default (their fingerprint collapses to n_layer alone — SSM models
# have no attn_q/ffn_gate/attn_k tensors — so a row would risk colliding with any future model of the same
# depth). Both measured CPU-decode-best anyway, which IS the default:
#   mamba2-130m-f16  (24/0/0/0)  CPU 64.88-67.77 vs r2 36.30
#   mamba2-2.7b-q8   (64/0/0/0)  CPU 6.47        vs r2 6.09
